## 3. 方案 A 四阶段（A0–A3）RTX A6000 48GB 精细 GPU 耗时账本

显式计入：**新视频解码与抽帧 + X-CLIP 抽特征 + VideoUFO 检索与 D 重排 + Video-LLaMA EVA/Q-Former 视觉特征提取 + 每次冷启动 + 现代 VLM 首次加载/视频视觉 token 预算 + 本地裁判精确调用次数**。

### 3.1 各环节参数假设（RTX A6000 48GB 保守口径）

- **视频解码与 16 帧抽样**（30 条 DREAM-1K + 20 条 VidHalluc，平均 ~10 s/条）：CPU/IO 解码 ~1–2 s/视频（含落盘验证）。
- **X-CLIP 抽特征 + VideoUFO 检索 + D 重排**：X-CLIP 视觉编码 ~0.5 s/视频；对 VideoUFO 冻结向量索引（约 500K–1M 级）执行 top-20 检索 + D 质量重排（CPU/GPU 混合，冷启动加载索引 ~1–3 min）→ 30 条视频合计 **~5–10 min（0.08–0.17 h）**。
- **Video-LLaMA 视觉特征提取（EVA-CLIP + Q-Former，16 帧）**：冷启动 ~40 s + 约 1.5–2.5 s/视频 → 30 视频约 **~2 min**，20 视频约 **~1.5 min**。
- **Video-LLaMA 生成推理（A6000 实测锚定）**：
  - A1（30 条 DREAM-1K × 3 臂 `A0/A1/A7` = 90 次生成）：3 次进程冷启动（~3.3 min）+ `30×(1.44+1.55+2.88) = 176 s`（~3.0 min）≈ **~6.5 min（0.11 h）**；
  - A3（20 条 VidHalluc × 4 臂 `Base/Sup/Con/Neu` = 80 次生成，均为单句提示约 1.6 s/次）：4 次冷启动（~4.4 min）+ `80×1.6 = 128 s`（~2.1 min）≈ **~6.5 min（0.11 h）**。
- **现代 VLM（`Qwen2.5-VL-7B-Instruct`, BF16, ~15.5 GB VRAM）**：
  - 帧数与视觉 token 上限显式锁定：**均匀 16 帧**（与 Video-LLaMA 帧数口径一致），单帧视觉 token 上限控制在 **256–384 tokens**（总视觉上下文约 **4,096–6,144 tokens**，安全运行于 48 GB VRAM，实测无 OOM）；
  - 首次加载与编译/热身（含 5 条 smoke 显存探测）：**~2–4 min**；
  - 短字幕（8–18 词，约 20–30 output tokens）单次 A6000 48GB 推理耗时（prefill 4K–6K visual tokens + decode 30 tokens）：保守按 **2.5–4.5 s/次** 估算；
  - A3 共运行 `30×3`（DREAM-1K）+ `20×4`（VidHalluc）= **170 次生成** → `170 × (2.5–4.5 s)` = `7.1–12.8 min` + 启动/热身 ~4 min ≈ **~11–17 min（0.18–0.28 h）**。
- **本地跨家族三值 NLI 裁判精确调用次数与耗时（RTX A6000 48GB，vLLM 静态批处理）**：
  - **重要优化**：DREAM-1K `DREAM-1k.jsonl` 已自带参考端 `events`；仅需对**生成字幕**执行事件拆解 + 三值 NLI 核验，以及对预抽 1–2 条 `R_core_ref` 核心事件做反向召回核验：
    - **A2（90 条 Video-LLaMA DREAM-1K 字幕）**：
      - 步 1（预测事件拆解）：`90` 次调用；
      - 步 2（预测事件 vs 参考文本三值 NLI，每条短字幕平均 2–4 个原子事实，按整句打包或逐事实调用）：整句 JSON 打包 = `90` 次（若逐事实拆开 = `~270` 次）；
      - 步 3（预抽 1–2 核心参考事件 vs 预测字幕召回 NLI）：`90` 次（或逐事件 `~150` 次）；
      - 步 4（A2 最多 2 轮提示词校准重跑）：总调用量 = **270–510 次/轮 × 最多 2 轮 = 540–1,020 次 LLM 调用**。
      - 在 RTX A6000 48GB 上以 24B–27B AWQ 模型（vLLM 吞吐保守 ~25–45 tok/s，单次输出 ~120–180 tokens，含 1.5 min 模型加载）：约 **~0.25–0.55 GPU 小时**（若使用 70B-AWQ 则为 **~0.50–1.00 GPU 小时**）。
    - **A3（90 条现代 VLM DREAM-1K 字幕 + 160 条 VidHalluc 字幕双盲单目标 E3 核验）**：
      - DREAM-1K 现代 VLM 90 条（固定冻结提示词，仅跑 1 轮）：`270–510` 次调用 ≈ **~0.15–0.30 GPU 小时**；
      - VidHalluc 160 条 × 双盲单目标 2 次独立调用（分别验 $Y^+$ 与 $Y^-$）= **`320` 次调用**（短 JSON 输出 ~60 tokens）≈ **~0.08–0.18 GPU 小时**。

## 5. 五类失败区分原则（严格禁止“拿试点显著性否决课题”）

每次阶段门控评审必须先将任何异常归类到以下五类之一，**严禁混为一谈**：

1. **`DATA_UNAVAILABLE`（数据不可用）**：gated 权限无法通过、许可证限制阻断内部运行、下载损坏、视频解码大面积失败、或 DREAM-1K 近重复排除后剩余合规样本 `< 600`；
2. **`MODEL_INCOMPATIBLE`（模型不兼容）**：RTX A6000 48GB OOM、隔离 Conda 环境依赖冲突、或现代 VLM 无法服从 8–18 词短字幕长度控制（均值 $> 25$ 词或高频空输出/重复退化）；
3. **`EVALUATOR_UNRELIABLE`（评价工具不可靠）**：触碰 `UARCap_Q2_EVALUATOR_VALIDATION_PROTOCOL.md` 第 3.3 节任一红线（尤其是 `A7` 系统漏检差分偏置或 `Unmentioned` 暗藏大量真实错误）；
4. **`SCIENTIFIC_NULL_EFFECT`（实验结果阴性）**：例如 20 条 VidHalluc 上 `Con vs Neu` 未达 $p < 0.05$，或 30 条 DREAM-1K 上 `A7 vs A0` 差异很小或方向不显著。**此项明确定义为“非失败”——试点仅检流程与测量可靠性，绝不以 20–30 条样本的显著性决定是否放弃科学问题！**
5. **`RESOURCE_UNACCEPTABLE`（资源成本不可接受）**：按方案 A 实测单视频 GPU 秒数与双人分钟数外推正式方案 B 后，发现总 GPU 超过 **45 GPU 小时** 或双人总人时超过 **70 总人时** 且无法通过合法裁剪次要臂压回预算内。
